Vitalos Technologies · Architecture

Answerd

The UK local services marketplace where every business picks up. This repo ships two front ends on Cloudflare Workers: a clickable prototype that simulates every surface of the product against one browser store, and the app-first Answerd website. The real backend is the Answerd API in Workforce, which both apps reach only in API mode.

Server

Security

Trust boundaries, authentication and authorisation, secrets handling and data protection.

Auth

Authentication

Mock mode: personas from the hub; any code but 000000 passes; five wrong codes lock a number for 15 minutes. API mode: phone number and SMS code through the Answerd API, with one token refresh on a 401.

Sessions

Token storage

Website: answerd_at (1 hour) and answerd_rt (30 days) as httpOnly, SameSite Lax cookies, Secure in production, set by Server Actions. Prototype: localStorage, as a stand-in for the app's keychain.

Access

Authorisation

Enforced by the Answerd API. The prototype mirrors the spec's permission table (guest to admin) in the UI only and holds no real data. Every admin write needs a reason and is audited.

Webhooks

Signed in and out

Revalidate: HMAC-SHA256 over timestamp and body, constant-time compare, 5 minute window. Contact relay: Origin check, 32 KB cap, field and control-character checks, honeypot, optional Turnstile, HMAC signature, body never logged.

Secrets

Where they live

Worker secrets for the contact relay, revalidation and the optional model key; GitHub Actions secrets for the Cloudflare token and staging test numbers. The deploy checks they exist without printing them.

Privacy

Consent and third parties

Equal-weight cookie choices. The Askbridge widget loads only after the visitor allows chat. Google results carry attribution and are never cached. All demo people and numbers are fictional.

Website READMEStandalone project that never imports from the prototype; read-only static-assets cache, no paid R2; Google results never cached; Server Actions because of the API's CORS.
API contract (stand-in)What staging confirmed on 27 Oct 2026, until the Workforce backend spec and @vitalos/answerd-client can be read here (issue #2).
README, From prototype to MVPExpo app for both modes, Next.js web, admin with Google sign-in, Workforce backend for data, the desk and billing, Ask Answerd powered by Askbridge.
No security headers. Neither Next.js config sets a Content-Security-Policy, frame or referrer policy, and there is no _headers file, so only Cloudflare's defaults apply.
Prototype token handling. In API mode the prototype keeps tokens in localStorage and passes the access token to its realtime relay in the query string, because EventSource cannot set headers. Fine for a demo that runs in mock mode in production; it must not carry over to the MVP.
API contract not confirmed. Authenticated request bodies are unverified because staging answers 401 before validating, and two hand-written clients stand in for @vitalos/answerd-client, so they can drift from the backend.
Unpinned actions. ci.yml and update-answerd-client.yml use version tags; deploy.yml pins SHAs.
Doc drift. The deploy handoff still links issues on answerd-prototype, the repo's old name. The prototype sends the realtime token as ?access_token= plus a bearer header, while Workforce's infrastructure README documents ?token=. The README says Ask Answerd will be powered by Askbridge, while the prototype's optional parser calls the Anthropic API directly. The deploy filter counts arch/index.html as a prototype change, so updating this page triggers one redeploy of an unchanged build.
